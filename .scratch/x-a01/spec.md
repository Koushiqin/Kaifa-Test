## Problem Statement

作为 ExamGuru 测试工作台的测试员，我需要执行 X-A01 的三个用例：四角色合法登录与默认入口、无效与过期会话、退出后旧请求。当前没有管理员账号、候选版本未知、被测站点的隔离性待核实，而且三个用例都以“教师、助教、学生、管理员四类角色”为前提。如果只靠手工点击，我无法稳定复现同一轮执行，也无法保证证据完整；更危险的是，容易把可用三角色的部分通过写成整体通过，或者把模拟无效会话当成真实过期。

我需要一份可执行、可审计的测试计划：它能在一次 45–70 分钟的运行内完成三个用例，按角色隔离会话、识别实际会话载体、记录真实证据，并按工作台官方 schema 生成结果；对于无法验证的断言，必须如实记为 `blocked` 或 `na`，而不是猜测通过。

## Solution

本轮测试计划是：用一个 X-A01 专用 Playwright 执行器，使用真实 Chrome 和每个角色独立的 browser context，完成三个用例的外部行为验证，并产出：

- 一份符合工作台官方结果 schema 的结果文件；
- 一份脱敏证据目录和 manifest；
- 一份简短的中文报告。

计划在开跑前完成预检（站点、账号、负责人、revision、会话载体、身份接口、合法读写对象、管理员角色/入口），执行中按用例记录状态和 note，执行后做证据自检和 schema 校验。管理员缺失时，先确认站点是否存在管理员角色/入口，再决定 `blocked` 或 `na`；真实 TTL 不可验证时，明确记录“模拟无效，不是真实过期”。结果先本地生成，未经明确授权不导入工作台。

## User Stories

1. 作为 X-A01 测试员，我希望用一条命令重复执行三个用例，以便同一候选版本可以复测。
2. 作为 X-A01 测试员，我希望每个角色使用独立 browser context，以便会话不串。
3. 作为 X-A01 测试员，我希望按账号键读取账号，以便密码不写进脚本。
4. 作为 X-A01 测试员，我希望记录站点返回的实际角色，以便不假设 `<测试账号>` 就是助教。
5. 作为 X-A01 测试员，我希望记录每个角色的默认落地页和可见入口，以便判断默认入口是否合法。
6. 作为 X-A01 测试员，我希望区分“管理员账号缺失”和“管理员角色/入口不存在”，以便正确记 `blocked` 或 `na`。
7. 作为 X-A01 测试员，我希望错误凭据只尝试一次，以便不锁定测试账号。
8. 作为 X-A01 测试员，我希望验证无会话访问受保护资源被拒，以便确认匿名访问边界。
9. 作为 X-A01 测试员，我希望识别实际会话载体，以便退出和过期测试不遗漏 localStorage、sessionStorage 或 Authorization。
10. 作为 X-A01 测试员，我希望先记录会话 exp，再在等待期间做其他子场景，以便 5 分钟预算不浪费。
11. 作为 X-A01 测试员，我希望真实 TTL 不可验证时明确记 `blocked`，以便不把模拟无效写成真实过期。
12. 作为 X-A01 测试员，我希望有一个确定的合法读写对象，以便退出后重放测试的是真实操作。
13. 作为 X-A01 测试员，我希望优先使用幂等写，以便重放不制造重复数据。
14. 作为 X-A01 测试员，我希望用每种旧会话载体重放读和写，以便发现“只失效 cookie、不失效 token”的缺陷。
15. 作为 X-A01 测试员，我希望在刷新前检查旧页面是否仍显示数据，以便发现内存残留。
16. 作为 X-A01 测试员，我希望重放后核对数据状态，以便确认旧写没有生效。
17. 作为 X-A01 测试员，我希望截图和响应摘要脱敏，以便证据不含密码、token 或学生 PII。
18. 作为 X-A01 测试员，我希望证据有 manifest 和 hash，以便报告可追溯。
19. 作为 X-A01 测试员，我希望结果文件符合工作台官方 schema，以便工作台能校验。
20. 作为 X-A01 测试员，我希望三个用例都有状态和 note，以便导入不会被拒。
21. 作为 X-A01 测试员，我希望 `build` 记 `unknown`、日期和指纹进 `notes`，以便不伪造候选版本。
22. 作为 X-A01 测试员，我希望 `environment` 标明隔离性待核实，以便不把非隔离结果当隔离验收。
23. 作为 X-A01 测试员，我希望导入前重读 revision，以便避免 409。
24. 作为 X-A01 测试员，我希望只在明确授权后通过 UI 导入，以便不误写共享记录。
25. 作为 X-A01 测试员，我希望失败、阻塞、不适用都有明确判定规则，以便部分通过不被写成 `passed`。
26. 作为 X-A01 测试员，我希望遇到账号锁定、反爬或数据风险时停止，以便不造成损害。
27. 作为 X-A01 测试员，我希望补管理员后按新 `runId` 重跑，以便保留旧 `blocked` 记录。
28. 作为测试负责人，我希望报告列出管理员、候选版本和隔离性缺口，以便判断 P0 是否能放行。
29. 作为未来测试员，我希望账号库和执行器模式可复用，以便其他编号任务不必重复造轮子。
30. 作为安全审查者，我希望原始 HAR 只存在本地忽略目录，以便不会误提交 token。
31. 作为评审者，我希望报告说明权限矩阵缺失和 A-A01 基线，以便“只出现允许入口”不被过度断言。
32. 作为评审者，我希望报告区分“产品缺陷”和“环境/账号缺口”，以便修复责任清晰。
33. 作为测试负责人，我希望开跑前完成入口条件检查（站点、账号、负责人、 revision、会话载体、读写对象），以便不在无效配置上开始。
34. 作为测试负责人，我希望退出条件是“三个用例都有状态和 note、证据完整、结果 schema 通过”，以便即使全部 blocked 也能审计。
35. 作为测试员，我希望执行时间盒把 TTL 等待限制在 5 分钟，以便不占用整轮 45–70 分钟。
36. 作为评审者，我希望看到一张用例状态摘要表（通过/失败/阻塞/不适用 + 原因），以便快速判断是否需要补账号重跑。
37. 作为工作台负责人，我希望结果默认不自动导入，以便共享记录只在明确批准后变化。
38. 作为未来测试员，我希望 `runId`、`expectedRevision` 和证据索引被记录，以便复现同一轮运行。

## Implementation Decisions

### Test Plan

- **范围**：只执行 X-A01-01/02/03；不扩展到其他自动任务。
- **环境**：被测站按 `exam.1mpower.com` 处理；用户确认非隔离，但工作台任务卡写“隔离测试环境”，存在冲突。预检记录隔离性证据；取得证据后按证据更新 `environment`，未取得证据前写“测试环境，隔离性待核实”。
- **账号**：教师、助教、学生共 5 个测试账号；没有管理员账号。管理员按“账号缺失但角色存在 → `blocked`；角色/入口不存在 → `na`”判定。
- **执行时间盒**：预检 10 分钟，X-A01-01 15 分钟，X-A01-02 15 分钟，X-A01-03 15 分钟，证据与结果 10 分钟，复核 5 分钟；总计 45–70 分钟。工作台给 X-A01 的 15 分钟是人工准备与复核估计，不等于整轮执行时间。
- **入口条件**：站点可达、登录页正常；账号库包含全部账号键；工作台负责人是测试员 B、任务已领取/进行中、revision 可读；会话载体已枚举；身份接口已确认或有 fallback；合法读写对象已确定；管理员角色/入口已预检。
- **退出条件**：三个用例都有状态和 note；证据已脱敏并生成 manifest；结果文件通过官方 schema 校验；中文报告完成；未授权不导入工作台。即使全部为 `blocked` 或 `na`，也必须满足退出条件。
- **角色与审批**：测试员 B 执行并记录；用户/测试负责人批准最小写操作、执行范围和导入；工程负责人按需提供候选版本 commit 或管理员账号。
- **交付物**：结果文件、脱敏证据目录及 manifest、中文报告、可复用执行器。

| X-A01-02 无效与过期会话 | 错误凭据一次；无会话访问；过期/无效会话；学生+教师覆盖；助教实际角色有效时覆盖；管理员按判定树 | 被拒；反馈可理解；不泄露账号是否存在；不返回业务数据；不下发有效会话 | 接受错误凭据/泄露数据 → `failed`；真实 TTL 未验证 → `blocked`；管理员账号缺失但角色存在 → `blocked`；无管理员角色/入口 → `na` |

### Harness and Seams

- 执行器采用 Node.js + Playwright，驱动真实 Chrome；每个角色一个独立 browser context，不共享 cookie 或 storage。
- 真实运行的 seam：浏览器 UI（登录、默认入口、导航、旧页面刷新）+ 目标站 HTTP API（身份、受保护资源、读写、会话重放）。不依赖被测站内部实现。
- 执行器自身逻辑（状态判定、脱敏、schema 校验、runId/revision 处理）用纯函数和 fixture 测试，不新增网络 fixture seam。
- 账号库是仓库级共享的本地 JSON，按账号键读取；脚本只接收账号键，不接收明文密码。账号库含 `displayName`、`username`、`password`、`expectedRole`。

### Identity and Permissions

- 身份接口：预检已记录 `GET /api/v1/me` 未认证返回 401（2026-11-26 16:48:58 +08:00，`UNAUTHENTICATED`，本地预检证据）；登录后返回结构待预检确认，确认不了就用会话 claims + 页面身份元素交叉验证。
- 权限基线：工作台引用的 `docs/95-assistant-role-and-shared-work.md` 当前 404；A-A01 前置条件摘要作为唯一可用基线（同机构全部学生与作业、不限发布人；发布/查看/修改/撤回/结束同机构作业、上传批改人工确认；账号创建/角色/密码仅管理员）。没有基线的入口只记录，不判失败。
- “角色单列阻塞”操作化为：该角色默认落地页不是空壳/无权限页，且能看到自己的核心入口；无法判定时记录观察或 `blocked`，不硬判失败。
- 助教入口与教师/学生的差异只作为观察项，不判失败；任务有依据的断言是“低权限角色看不到高权限入口、教师看不到管理入口”。

### Sessions and Data

- 会话载体：预检枚举 cookies、localStorage、sessionStorage、IndexedDB（如有）、Authorization；X-A01-03 按每种旧载体重放。
- 过期验证：先登录记录 cookie/JWT exp，再做其他子场景；最多等 5 分钟。超过预算则模拟无效，明确标注“模拟无效，不是真实过期”；无可观测 TTL 记 `blocked`。
- 合法读写前置：优先由测试教师给测试学生新建一个最小作业/草稿，避免碰真实教师/班级的数据；只有在确认现有作业属于测试教师/测试班级且可安全修改时，才使用已有作业。优先幂等写（客户端 ID、PUT/PATCH、无变化更新）；结束后清理。
- 错误凭据只尝试一次，优先使用次要学生账号，避免锁定主账号。

### Result and Status

- 状态判定优先级：`failed` > `blocked` > `passed`。管理员账号缺失但角色/入口存在 → `blocked`；角色/入口不存在 → `na` 附证据；助教实际角色不符 → 先记录实际角色，再按角色是否存在判 `blocked`/`na`。
- 候选版本：`build` 写 `unknown`，日期、响应头、静态资源 hash 写 `notes`；候选版本未知是任务级限制，不直接改用例状态。
- 结果 schema：官方 X-A01 模板；`expectedRevision=1`、`measurementScope=functional`、`metrics={}`、`thresholds=[]`、`artifacts=[]`；`caseResults` 覆盖全部三个用例，失败/阻塞/不适用必须有 note。
- 导入：只通过工作台 UI 或受支持的站点访问；不直接 curl `/api/results`。导入前用浏览器上下文重读 revision，确认当前身份是测试员 B，且获得明确授权。
- 工作台 `storage: shared`，导入会写团队共享记录；结果默认本地生成。

### Evidence and Reporting

- 证据：截图 + 脱敏请求/响应摘要；原始 HAR 只放本地忽略目录；证据目录含 manifest，记录时间、URL、状态码和 SHA256。
- 脱敏：密码、cookie、set-cookie、Authorization、token、session、csrf、username、displayName、studentId、email、phone、班级/学校名称全部移除或打码。
- 报告：中文 Markdown，包含用例状态摘要表、环境/版本缺口、角色/入口矩阵、证据索引、阻塞原因和下一步。

### Safety

- 安全停止条件：站点不可达、连续 5xx、账号锁定、反爬挑战无法通过、出现影响他人数据的风险、写入无法清理。
- 不做压测、fuzz、越权扫描；只做最小写操作；不接触其他账号数据。

## Testing Decisions

- 好的测试只验证外部行为：登录是否成功、身份/角色是否与站点返回一致、默认入口是否合法、导航是否暴露高权限入口、HTTP 是否拒绝、是否返回业务数据、数据是否变化、结果文件是否符合 schema。不断言内部实现细节。
- 覆盖 seam：
  - X-A01-01：浏览器 UI（登录、默认入口、导航）+ 身份接口；
  - X-A01-02：浏览器 UI + HTTP API（错误凭据、无会话、过期/无效会话）+ 会话载体；
  - X-A01-03：浏览器 UI + HTTP API（合法读/写、退出、旧载体重放）+ 数据状态。
- 执行器自身逻辑的测试：状态判定（failed/blocked/passed/na）、管理员/助教判定树、脱敏、schema 校验、runId/revision 处理。优先用纯函数和 fixture JSON 测试，不依赖被测站。
- 真实 X-A01 运行作为集成测试，直接在真实站点上执行；不 mock 目标站，以免掩盖真实会话行为。
- 先例：仓库没有现成的执行器测试；工作台的 `/api/results/schema` 模板、X-A01 官方结果模板、A-A01 前置条件摘要是最接近的“先例”。结果文件写入前用官方模板做本地校验。
- 每次运行前做 dry-run：检查账号键、必需配置、证据目录、结果 schema；不打印密码。
- 每次运行后做证据自检：确认没有密码、cookie、Authorization、token 或学生 PII；确认 manifest hash 与文件一致。

## Out of Scope

- X-A01 之外的其他 38 项自动任务（A-A01、G-A01、P-A01 ~ P-A18、S-A01、S-A02、T-A01 等）。
- 压测、容量测试、fuzz、渗透测试、服务端越权扫描；服务端授权问题属于 A-A01 等任务。
- 修复被测站缺陷；本轮只记录发现。
- 未经明确授权把结果导入工作台。
- 创建管理员账号、修改角色/密码、提权。
- 使用真实学生数据；只使用账号库中的测试账号。
- PDF 验收、人工验收、正式题库导出。
- 构建通用测试框架；只实现 X-A01 需要的能力，通用模块可复用但不追求通用框架。
- 等待超过 5 分钟的真实 TTL；超过预算按 `blocked` 记录。
- 跨账号数据隔离测试（属于 X-A02）。

## Further Notes

- 工作台 X-A01：P0、自动执行、3 个用例、负责人测试员 B、`started: true`、revision 1、记录 `environment` 为“测试环境”、`build` 为空。
- 官方 schema 的关键约束：`caseResults` 必须覆盖全部用例；未执行用例用 `blocked` 并说明；同一 `runId` 同内容幂等，不同内容 409；`expectedRevision` 是并发控制参数。
- 工作台 `storage: shared`，导入会写团队共享记录；结果先本地生成。
- 工作台权限矩阵链接 `docs/95-assistant-role-and-shared-work.md` 当前 404；不要凭空编造权限矩阵。
- 详细的分步执行流程、证据文件命名和时间盒在 X-A01 任务文件夹的执行方案中；本 spec 固定本次测试计划的目标、范围、决策和边界，避免重复维护。
- 本次测试计划预计结果：X-A01-01/02/03 至少为 `blocked` 或 `na`（按判定树）；发现缺陷则 `failed`。只有在管理员角色存在且拿到账号、候选版本可归因、真实 TTL 可验证时，才可能形成 P0 通过结论。
