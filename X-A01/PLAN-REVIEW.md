## 2. 详细审查

### R-01 候选版本只写 `unknown-2026-11-26`，未列为独立阻塞

**证据**

- [PLAN.md:201](PLAN.md#L201) 写 `build` 为 `unknown-2026-11-26`。
- [GLOSSARY.md:24](../GLOSSARY.md#L24) 明确：“没有 commit 时记为未知，不能用日期冒充版本。”
- 官方 schema 把 `build` 列为必填；工作台 P0 卡写“需核对同一候选版本”。
- 缓存记录里 X-A01 的 `build` 为空，说明当前没有候选版本。

**影响**

`unknown-2026-11-26` 虽然带 `unknown` 前缀，但仍把日期放进 `build` 字段，容易被当成版本；即使补了管理员，没有候选版本，P0 通过也无法归因到某次发布。方案 [PLAN.md:11](PLAN.md#L11) 把管理员说成唯一缺口，不完整。

**建议**

- `build` 写 `unknown`；日期、响应头、静态资源 hash 写 `notes`。
- 把“候选版本未知”加入 [PLAN.md:186](PLAN.md#L186) 的预期结果表和风险表，与管理员同级。
- 开跑前先向用户要 commit；拿不到就明确写“本轮不能形成 P0 通过结论”。

### R-02 环境前提与工作台冲突，且方案未给判定依据

**证据**

- [PLAN.md:6](PLAN.md#L6) 断言被测站是“非隔离共享环境”。
- [ADR-0001](../docs/adr/0001-x-a01-nonisolated-blocked.md#L6) 以“不是隔离环境”为前提。
- 工作台任务卡 `device` 是“隔离测试环境 / 浏览器与接口自动化”；缓存记录 `environment` 是“测试环境”。
- 账号表写“禁止向网站内其他账号执行数据操作”，这能说明站内存在其他账号，但不等于存在真实用户。

**影响**

如果站点实际是隔离测试环境，ADR 和风险表会高估风险；如果确实共享，工作台的任务前提不满足，结果不能直接当作隔离环境验收。两种情况下，方案都需要把“环境隔离性”写成待核实或附证据，而不是直接断言。

**建议**

- 预检时记录判定依据：站点是否只有测试账号、是否有真实班级/学生数据、是否有站点所有者说明。
- 在证据未取得前，`environment` 写成 `exam.1mpower.com（测试环境，隔离性待核实）`。
- 同步修订 ADR 与 [GLOSSARY.md:55](../GLOSSARY.md#L55) 的“被测站”定义；明确非隔离结果的适用边界。

### R-03 权限矩阵与“角色单列”不可判定

**证据**

- [PLAN.md:123](PLAN.md#L123) 写“工作台没有给出正式权限矩阵”。
- 工作台“执行节奏”页把“四端权限矩阵”链接到 `docs/95-assistant-role-and-shared-work.md`；A-A01 前置条件也摘要了矩阵（同机构全部学生与作业、账号创建/角色/密码仅管理员）。但该 GitHub raw 链接当前 404。
- “角色单列”只出现在 X-A01-01 的 expected 里；工作台和 GLOSSARY 都没有定义。

**影响**

“只出现权限允许的入口”没有可核对的矩阵；“不存在角色单列阻塞”不可判定。方案 [PLAN.md:120](PLAN.md#L120) 把它改写成“合法角色不被角色单列挡住”，仍然是同义反复。

**建议**

- 把“没有给出”改成“工作台引用了 docs/95 矩阵，但当前链接 404；X-A01 任务本身没有逐入口矩阵”。
- 用 A-A01 的摘要作为唯一可用基线，逐条列出允许/禁止入口；没有基线的入口只记录、不判失败。
- 给“角色单列”下可观察定义，例如：默认落地页不是“无权限/未配置”空页；导航项不是按角色单列的空壳；或明确标为“无法判定，记 blocked”。

### R-04 会话载体只覆盖 cookie，X-A01-03 可能测不到真正的旧会话

**证据**

- [PLAN.md:133](PLAN.md#L133) 只读 cookie 属性和 JWT `exp`。
- [PLAN.md:153](PLAN.md#L153) 只记录“会话 cookie”。
- 目标站登录页是传统用户名/密码表单，但登录后是否改用 localStorage bearer token 尚未确认。

**影响**

如果 SPA 把 token 放在 `localStorage`/`sessionStorage`/`Authorization`，只重放旧 cookie 会漏测；退出后旧 token 可能仍然有效。另外“未生成新会话”过严：匿名会话 cookie、CSRF cookie 是正常的；“旧读必须 401/403”也过严：页面请求可能 302 跳登录。

**建议**

- 预检时枚举会话载体：cookies、`localStorage`、`sessionStorage`、IndexedDB（如有）、`Authorization` 头。
- X-A01-03 分别用每种旧载体重放；断言“没有有效认证会话、没有业务数据”，不要求“没有任何新 cookie”。
- API 断言 401/403；页面断言 302 跳登录或登录页；核心断言是“无业务数据、无状态变化”。
- 退出后先检查旧页面是否仍显示数据，再刷新；只测刷新会漏掉内存残留。

### R-05 X-A01-03 缺少合法读写的确定性前置

**证据**

- [PLAN.md:152](PLAN.md#L152) 假设学生有“作业列表”和一个可保存的草稿。
- 工作台 X-A01 前置条件只要求四角色账号，没有要求测试学生已有作业。
- 共享环境中的测试学生可能没有任何作业，或作业属于其他测试者的数据。

**影响**

没有合法读写对象时，X-A01-03 的写重放会因“没有可写对象”而 blocked，不是产品缺陷；如果写接口不是幂等的，重放本身还可能造出重复数据。

**建议**

- 加一步前置：教师给测试学生发布一个最小作业（或使用测试账号自己已有的草稿），记录作业/草稿 ID。
- 选择天然幂等的写：带客户端 ID 的草稿保存、无变化更新，优先 PUT/PATCH。
- 结束后用教师/学生账号清理；清理不了就在 `notes` 写明“未清理”，并评估是否记 blocked。

### R-06 `.scratch/` 未加入 `.gitignore`

**证据**

- [PLAN.md:230](PLAN.md#L230) 说完整 HAR 只放 `.scratch/`。
- [.gitignore](../.gitignore#L1) 只忽略 `.secrets/`、`*.local.json`、`UsableAccounts.md`、`X-A01/evidence/`、`node_modules/`、`.claude/settings.local.json`，没有 `.scratch/` 或 `*.har`。

**影响**

一次 `git add .` 就可能把带 cookie/Authorization 的 HAR、探测脚本输出提交进仓库；`.scratch/` 目前还是未跟踪状态。

**建议**

- 把 `.scratch/` 或至少 `*.har`、`*.trace.zip` 加入 `.gitignore`。
- 运行后删除或脱敏 HAR；HAR 不进入交付物、不提交、不共享。

### R-07 `na` 与 `blocked` 的规则过粗

**证据**

- [PLAN.md:179](PLAN.md#L179) 写“`na` 不能用于缺管理员账号”。
- [GLOSSARY.md:43](../GLOSSARY.md#L43) 定义 `na` 是“产品明确不提供该角色或能力，且测试计划允许”。
- 工作台 X-M01-03 的 expected 也允许“未上线的助教/统计环节注明阻塞／不适用及原因”。

**影响**

“账号缺失但角色存在”和“产品根本没有管理员角色/入口”是两种不同情况。前者应 `blocked`，后者可能应 `na`；方案一律禁止 `na`，会把“角色不存在”误记成阻塞，也会让报告缺少“产品缺口”这个结论。

**建议**

使用下面的判定树：

- 管理员账号缺失，但站点存在管理员角色/入口 → `blocked`。
- 站点没有管理员角色/入口 → `na`，附证据。
- 助教账号登录后实际不是助教 → 先记录实际角色；再按“角色是否存在”判断 `blocked`/`na`。
- 产品明确不提供某能力，且任务允许 → `na`；不能用 `na` 掩盖没测到。

### R-08 额外断言可能造成假失败

**证据**

- [PLAN.md:112](PLAN.md#L112) 要求“助教入口是否与教师/学生区分”。
- 工作台 X-A01-01 的 expected 只要求“身份正确，只出现权限允许的入口；不存在角色单列阻塞”。
- A-A01 的权限矩阵只明确“账号创建/角色/密码仅管理员”，没有要求助教导航必须与教师/学生不同。

**影响**

如果产品有意让助教复用教师导航，方案会把它判成失败；这不是任务要求。

**建议**

- 保留有任务依据的断言：低权限角色看不到高权限入口；教师看不到管理入口。
- 把“助教导航是否与教师/学生不同”降级为观察项，只记录、不判失败。
- 把“权限泄漏”限定为入口可见性；服务端越权属于 A-A01，不在 X-A01 范围。

### R-09 TTL 等待与 15 分钟预算冲突

**证据**

- [PLAN.md:135](PLAN.md#L135) 说 TTL ≤ 10 分钟就等到过期。
- 工作台给 X-A01 的是 15 分钟“人工准备与复核”；方案 [PLAN.md:23](PLAN.md#L23) 的 45–70 分钟是整轮时间，不是任务级预算。
- [PLAN.md:238](PLAN.md#L238) 给 X-A01-02 只有 15 分钟。

**影响**

如果 TTL 恰好 10 分钟，光等待就吃掉 X-A01-02 的全部预算；之后再测错误凭据、无会话、其他角色会很仓促。

**建议**

- X-A01-02 开始时先登录一次，记录 cookie `exp`/JWT `exp`，然后去做错误凭据、无会话等用例；到时间再回来验证过期。
- 把等待阈值降到 5 分钟；超过 5 分钟就模拟无效并记 `blocked`，不要占满 15 分钟。
- 把“首次脚本开发/运行时间”和“工作台 15 分钟复核”分开写，不要用 30–90 分钟/轮证明任务级时间盒合理。

### R-10 `/api/v1/me` 硬编码

**证据**

- [PLAN.md:111](PLAN.md#L111) 写“`/api/v1/me`（或等价接口）”。
- [PLAN.md:118](PLAN.md#L118) 又写“以 `/api/v1/me` 为准”。

**影响**

如果站点没有这个路径，身份断言无法执行；如果路径变了，证据文件名也会对不上。

**建议**

- 预检时确认真实身份接口（网络面板/前端 bundle），把实际路径写进方案。
- 找不到身份接口时，用会话 claims + 页面身份元素交叉验证，并在 `notes` 说明。
- 证据文件名从 `01-me-<role>.json` 改成 `01-identity-<role>.json` 更稳妥。

### R-11 脱敏缺 PII，未测用户枚举

**证据**

- [PLAN.md:231](PLAN.md#L231) 只列 `password`、`cookie`、`set-cookie`、`authorization`、`token`、`session`、`csrf`。
- [GLOSSARY.md:60](../GLOSSARY.md#L60) 要求证据“不得包含密码、会话令牌或学生隐私”。
- 工作台结果接口要求 artifacts 不上传学生隐私或访问凭据。

**影响**

截图和响应摘要仍可能包含用户名、学生姓名、班级、邮箱、学号；错误凭据的反馈可能泄露“用户名是否存在”。

**建议**

- 脱敏清单补 `username`、`displayName`、`studentId`、`email`、`phone`、班级/学校名称。
- 截图对姓名、用户名、头像打码；JSON 只保留字段名、状态码和结论。
- 错误凭据断言：反馈可理解、不泄露账号是否存在、不下发有效会话；使用通用错误文案。

### R-12 负责人/领取状态与导入路径未记录

**证据**

- 缓存 [records.json](../.scratch/pw/records.json) 显示 X-A01 已由“测试员 B”领取、`started: true`、`revision: 1`。
- 方案没有提负责人或领取状态。
- 官方 schema 备注：外部自动执行器尚未配置机器密钥；`/api/records` 直接 curl 会被 Cloudflare 403。

**影响**

如果操作者不是测试员 B，可能在别人的任务上操作；如果计划用脚本直接 POST `/api/results`，会被访问策略挡住。

**建议**

- 确认当前操作者就是测试员 B；如果不是，先在工作台“安排与条件”协调领取。
- 导入前用浏览器上下文重读 `/api/records`，确认 revision 仍为 1；不要用 curl。
- 导入走工作台 UI，或先申请受支持的机器访问；不要假设 `/api/results` 可直接调用。
- 补管理员后按新 `runId` 重跑，保留旧 `blocked` 记录；同 `runId` 不同内容会 409。

### R-13 方案位置与 AGENTS 约定不一致

**证据**

- [AGENTS.md:3](../AGENTS.md) 规定 issues/specs 放在 `.scratch/`；[docs/agents/issue-tracker.md:3](../docs/agents/issue-tracker.md#L3) 要求 `.scratch/<feature-slug>/spec.md`。
- 方案实际在 `X-A01/PLAN.md`。

**影响**

如果 `PLAN.md` 被视为规格文件，它不在约定的 issue tracker 位置；如果被视为任务交付物，则没有问题。需要明确，否则后续 agent 可能找不到它。

**建议**

- 在 `X-A01/PLAN.md` 开头注明“本文件是 X-A01 任务交付物，规格索引见 `.scratch/x-a01/spec.md`”，或在 `.scratch/x-a01/spec.md` 建一个指向它的短文件。
- 不要把同一份内容复制两份，避免版本漂移。

## 3. 判定规则建议

| 场景 | 用例状态 | 说明 |
|---|---|---|
| 管理员账号缺失，但站点存在管理员角色/入口 | `blocked` | 附“未提供管理员账号” |
| 站点没有管理员角色/入口 | `na` | 附 UI/接口证据，说明产品缺口 |
| 助教账号实际不是助教 | 记录实际角色 | 助教相关断言按“角色是否存在”判 `blocked`/`na` |
| 候选版本未知 | 不直接改用例状态；`notes` 标明 | 即使断言通过，也不能形成可归因的 P0 通过结论 |
| 环境隔离性未确认 | 不直接改用例状态；`notes` 标明 | 不能作为隔离环境验收 |
| 旧读/旧写仍成功 | `failed` | 会话未失效，保留证据 |
| 旧页面仍显示数据，或刷新后仍可操作 | `failed` | 残留可操作身份/数据 |
| 写重放无法安全执行 | `blocked` | `note` 说明无法重放的原因 |
| 无真实 TTL 观测，仅模拟无效 | `blocked` | `note` 写“模拟无效，不是真实过期” |
| 错误凭据返回有效会话 | `failed` | 认证缺陷 |
| 无会话返回业务数据 | `failed` | 授权缺陷 |
| 错误凭据泄露账号是否存在 | `failed` | 用户枚举，安全缺陷 |
